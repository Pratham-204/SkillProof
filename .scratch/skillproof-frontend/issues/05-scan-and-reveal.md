# 05 — Scan & reveal experience

**What to build:** The centerpiece live view: a four-phase state machine (`idle | scanning | revealing | complete`) that consumes ticket 03's SSE stream, narrates repo names during scanning, and staggers Evidence Cards in one at a time as they complete, with a floored minimum duration so the effect never collapses.

**Blocked by:** 02, 03, 04.

**Status:** done

- [x] Phase state is a single `useState<Phase>`, no state library.
- [x] `scanning` phase opens the SSE connection from ticket 03 and renders each incoming repo name as it arrives; enforces a minimum 1.5s duration in this phase regardless of how fast real events arrive (real progress, floored — not simulated).
- [x] `revealing` phase consumes reveal (per-skill) SSE events; each arriving card animates in via Framer Motion (`staggerChildren` on the parent variant), not `setInterval`-based timing.
- [x] Score count-up uses `useMotionValue` + `animate` with a custom easing/deceleration curve (not `react-countup`), and the number element has `tabular-nums` applied (from ticket 02) so digit width doesn't jitter during the count.
- [x] A card with `evidence_type: "declared_only"` or `"none"` renders with a visually distinct treatment from `"verified"` — this is a domain distinction (see CONTEXT.md's Declared-Only term), not just a styling choice, and must not look like a full verified pass.
- [x] `complete` phase shows the full set of revealed cards, each expandable into the detail view from ticket 06.
- [x] A `/verify` run that partially fails (some skills `complete`, one `failed`) still reaches `complete` phase, with the failed skill's card showing its error rather than blocking the rest of the reveal.

## Comments

**Implementation:** `pages/ScanReveal.tsx` holds the four-phase machine. `idle` resolves identity via `getMe()`. `scanning` opens one native browser `EventSource('/verify/{candidateId}/stream', { withCredentials: true })` that stays open across the scanning→revealing transition (a single connection for the whole run, not recreated per phase) — `scan` events append repo names for narration; a `setTimeout(1500ms)` ref-flag plus a `done`-event ref-flag both have to be true before the phase can advance (`tryEnterRevealing`), so the floor and real completion combine via `max`, not either alone. `reveal` events fetch `GET /evidence-card/{candidateId}` and append just the newly-completed card to the `cards` array in real arrival order — cards are not pre-fetched as a batch at `done`; a `done` handler does one extra fetch afterward only to backfill any card that failed before ever producing its own `reveal` event (verify_service still marks failed cards in the same DB write path, but a failure short-circuits before that skill's normal reveal publish). `components/EvidenceCardTile.tsx` renders each card, with `declared_only`/`none` getting a dashed border + muted/60%-opacity treatment distinct from `verified`'s solid card, and a `failed` status getting its own red error tile. `components/ScoreCounter.tsx` is the `useMotionValue` + `animate` count-up (cubic-bezier `[0.16, 1, 0.3, 1]`, a standard "ease-out-expo"-like deceleration curve) with `tabular-nums`.

The list is wrapped in a `motion.ul` with `variants={{ visible: { transition: { staggerChildren: 0.32 } } }}` per the design brief. Worth being precise about what this does now that reveal is driven by real per-skill events rather than a fixed, pre-known set: Framer's `staggerChildren` staggers children that mount together within the same reconciliation pass — so when multiple skills resolve close together in real time (the common case, since the backend's per-skill scoring loop runs fast), they still get a genuine staggered entrance; a card that arrives seconds after the previous one just plays its own entrance on real arrival, which is arguably a *better* stagger than a fabricated fixed cadence would be. This is a deliberate reading of "staggerChildren, not setInterval" — the animation primitive is real, but it's layered on top of real event timing rather than replacing it.

**Known gap:** if this page is reached directly (a hard refresh, or a bookmark) rather than via the claim form's `navigate('/scan', { state: { skills } })`, `claimedSkills` is empty and the completion check falls back to "done + at least one card" instead of an exact count match. This is an accepted, disclosed limitation, not a silent bug — reconnecting to an in-progress or already-finished run via a lost-state page load isn't otherwise handled in this pass.

**Not yet done (ticket 06's scope):** cards aren't actually expandable yet — `EvidenceCardTile` is a summary tile only; clicking through to source commits/PR comments and the lazy `/explain` fetch land in the next ticket.

**Bug found and fixed via this live run:** the Python card's real evidence landed in a state no fixture had exercised — `evidence_type: "verified"` (real commits gave it a nonzero score from Presence/Volume/Span) but zero Depth-qualifying items (`source_commits: []`, since no single commit/PR-comment cleared the 0.35 similarity floor). `explain_service.template_fallback` (used because no `SKILLPROOF_GROQ_API_KEY` is set) unconditionally said "so the confidence score is 0" whenever `source_commits` was empty — wrong here (real score was 0.2667), and also wrong for any `declared_only` card, which always has empty `source_commits` by definition but a nonzero Presence-only score. Fixed in `explain_service.py` to interpolate `card.confidence_score` instead of hardcoding 0; `tests/test_explain_service.py`'s `test_template_fallback_with_no_evidence` (which only ever asserted the literal character "0" appeared, trivially true even with the bug) was split into a zero-score case and a new nonzero-score regression case. Full suite (78 tests) passes; re-verified live in-browser that the fix produces the correct sentence.
