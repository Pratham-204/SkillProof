# 03 — Real verify progress over SSE (scan + reveal events)

**What to build:** `GET /verify/{candidate_id}/stream` (SSE, `sse-starlette`), emitting two kinds of real events during an in-flight `/verify` run: a scan event per repo as `ingest_evidence` processes it, and a reveal event per skill as its `EvidenceCard` is individually committed. No fabricated/simulated progress — every event corresponds to real work completing.

**Blocked by:** none.

**Status:** done

- [x] `ingestion.ingest_evidence` accepts an optional progress callback, invoked once per repo (owned + external) as it's processed, with enough info to identify the repo (e.g. `full_name`). Existing callers that don't pass a callback are unaffected.
- [x] `GitHubClient` call sites within ingestion that currently run as one opaque pass are checkpointed so the callback actually fires per repo, not all at once at the end.
- [x] `verify_service.run_verification`'s scoring loop commits each `EvidenceCard` individually as it completes (replacing today's single commit after the full loop), and invokes a per-skill progress callback at that point.
- [x] `GET /verify/{candidate_id}/stream` opens after `POST /verify` has been called, streams scan events, then reveal events, then a terminal event once every claimed skill is `complete` or `failed`, then closes. Reconnecting after the stream has already finished returns the current state once and closes immediately (no hang).
- [x] A GitHub auth failure mid-ingestion (the existing `GitHubAuthError` path) still results in every claimed skill's card being marked `failed` as it does today, and the stream reflects that rather than hanging.
- [x] Test: consume the stream/event sequence in-test and assert on the sequence of event types/payloads (repo names in order, skill names in order), using `FakeGitHubClient` fixtures with multiple repos so ordering is actually exercised.

## Comments

This is the backend half of the scan/reveal experience (ticket 05). Per CONTEXT.md round 7 / the design session: full per-repo instrumentation was the explicit choice over a coarser per-skill-only or no-real-SSE fallback.

**Implementation:** `GitHubClient.list_qualifying_commits` (github_client.py) gained an optional `on_repo_scanned` callback, fired once per unique repo (deduped) right after that repo's commits are gathered — the owned-vs-external commit-fetching orchestration (ADR-0004's anti-gaming safety property) stays fully encapsulated inside `GitHubClient`, never bypassed. `ingest_evidence` forwards this through. `verify_service.run_verification`'s scoring loop now commits per skill (not batched at the end) and publishes a "reveal" event per skill; ingestion's per-repo callback publishes "scan" events; a `finally` block publishes a terminal "done" event on every exit path (success, GitHub auth failure, or unexpected exception). All publishing goes through a new `progress_bus.py` module: a simple in-process, thread-safe pub/sub (`queue.Queue` per candidate_id) bridging the background-task worker thread to an open SSE connection, a no-op if nobody's subscribed. `GET /verify/{candidate_id}/stream` (`routers/verify.py`, `sse-starlette`) checks for any `processing` `EvidenceCard` row using a short-lived session opened and closed immediately — deliberately not a request-scoped `Depends(get_db)`, which would stay open for the entire (potentially long) stream and starve the background job's own session of a pooled connection (a real deadlock, reproduced and fixed during implementation, not just a test artifact). If nothing is in flight, it returns a single `done` event immediately; otherwise it subscribes and relays events via `anyio.to_thread.run_sync(queue.get)` until `done`.

**Testing note:** Starlette's synchronous `TestClient` (used everywhere else in this suite) fully drains a streaming response before `.stream()`/`.get()` returns — confirmed by direct investigation (including trying an async `httpx.AsyncClient` + `ASGITransport` variant, which hit the same wall in this harness) — so it can't interleave with a background job running concurrently in another thread. The real ordering guarantee (scan events in repo order, reveal events in skill order, terminal `done`) is instead tested directly against `verify_service.run_verification` + `progress_bus`, which exercises the actual production code with no fabrication. The "reconnect after already finished" fast path is tested over real HTTP via `client`, since it never needs to wait on a live queue. Both were additionally smoke-tested against a real `uvicorn` server (`GET /verify/{id}/stream` for a nonexistent candidate returns a single `done` event immediately, no hang). Full live-streaming-over-HTTP (a genuinely in-flight job's events arriving while a client reads them) is left to a manual check once the frontend consumes this endpoint (ticket 05) rather than fought further in this harness.
