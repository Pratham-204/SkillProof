# Postgres is production-only; local development keeps SQLite unchanged

Production needs a database that survives a container being torn down and rebuilt — Railway's own filesystem isn't guaranteed persistent across deploys, and the app's container restarts routinely (every push to `main`, ticket 03). Local development has no such requirement: `uvicorn --reload` runs in one long-lived process, and introducing a local Postgres instance (or Docker Compose to run one) would add setup friction to the existing zero-infrastructure dev loop for a persistence guarantee nothing in dev actually needs. `Settings.database_url` therefore keeps its `sqlite:///./skillproof.db` default for every environment except production, where Railway's managed Postgres addon injects a real connection string.

The addon injects that connection string as a bare `DATABASE_URL`, not a `SKILLPROOF_`-prefixed one — `Settings`' blanket `env_prefix="SKILLPROOF_"` doesn't cover it, so `database_url` needed an explicit `validation_alias` accepting both names (`SKILLPROOF_DATABASE_URL` still winning if both are ever set). This gap was not caught by ticket 01's own tests, which exercised `make_engine()` directly with explicit connection strings rather than through `Settings`' actual environment-variable binding — it surfaced only when ticket 05's live persistence check found that two GitHub logins minutes apart against the deployed app produced two different `candidate_id`s, proving every redeploy was quietly starting from an empty, ephemeral SQLite file with the real Postgres addon sitting unused beside it.

## Consequences

SQLite and Postgres diverge in real, if usually minor, ways (type coercion, transaction isolation semantics, concurrent-write behavior), and nothing in this setup runs the test suite against Postgres — that divergence is an accepted, documented risk rather than one this decision solves. A schema or query that happens to work against SQLite locally is not guaranteed to behave identically against production Postgres; catching that gap currently depends on the ticket 02 Docker smoke test and manual verification after each deploy, not an automated Postgres-backed test run.
