# A new Signal that needs data GitHub doesn't already give ingestion must have its per-repo API cost budgeted before implementation, not discovered after

Provenance Check (round 11, ADR-0012, implemented in `bc1e282`) added two new `GitHubClient` calls per owned, non-fork repo: `get_earliest_commit_sha` (a paginated REST call) and `commit_exists_elsewhere` (a `/search/commits` call). The module itself was well-scoped — a single `provenance.py` function consuming an `EvidenceBundle` and returning a filtered one, called once from `verify_service.py` — and its own ticket's manual live-data verification passed cleanly. It was still reverted (`39fdd58`) as "not production-ready." The ticket's own follow-up note names why: `commit_exists_elsewhere` hits GitHub's Search API limit (30 requests/minute) rather than the regular REST limit (5000/hour), and a real account with several owned repos saw `/verify` take roughly a minute, most of it spent on these two new calls rather than the pre-existing ingestion work.

This wasn't a design flaw in `provenance.py`, or evidence that `GitHubClient`'s abstract-method seam is the wrong place for a repo-level check — a signal that needs a fact GitHub doesn't hand back from calls ingestion already makes will always need a new call somewhere, and `provenance.py` isolated that call cleanly. What was missing was costing the call's request volume against GitHub's *per-endpoint* rate limits (not just the regular REST budget every other `GitHubClient` method already shares) before writing the fetch, the same way `github-scan-performance` tickets 01–03 budgeted concurrency and the shared rate-limit gate for the existing calls.

## Consequences

A future Signal that needs new per-repo or per-commit GitHub data (the self-extending taxonomy's planned Depth Interview and any multi-platform evidence sourcing are named as further-out ideas in `CONTEXT.md`'s Notes, and are the most likely next callers of this pattern) must state, before implementation, which GitHub endpoint(s) it calls, how many calls it adds per repo, and which rate limit bucket those calls draw from (regular REST vs. Search API vs. GraphQL's separate point budget) — and size that against the largest realistic owned-repo count, not just the fixture-sized manual test that passed here. A signal whose cost doesn't fit the budget needs a cheaper check (e.g. a heuristic pre-filter that skips the expensive call for repos unlikely to need it) designed in from the start, not added as a follow-up after a slow `/verify` call is already observed.
