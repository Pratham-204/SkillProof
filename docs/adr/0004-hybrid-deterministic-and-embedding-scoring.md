# Evidence scoring becomes a hybrid of deterministic signals and narrowly-scoped embeddings

Pure cosine similarity between a Skill Tag's embedding and a raw commit diff didn't work: sentence-transformer models are trained on natural language, and code diffs embed poorly against a skill's plain-English description. We decided to split evidence detection into four Signals — Presence (a dependency-manifest or file-extension match), Volume (commits touching files matching a Skill Tag's Detection Pattern), Depth (the one Signal that still uses embeddings, comparing PR comments and commit messages from Volume-qualifying commits against the skill's canonical description), and Span (the date range of the full qualifying evidence set) — combined as a fixed weighted sum (0.20 / 0.40 / 0.25 / 0.15) rather than a single similarity average.

## Consequences

Presence and Volume require every taxonomy entry to carry a hand-authored Detection Pattern (package identifier, import pattern, API surface marker, config filename, or file extension); a Skill Tag with no such pattern — a purely theoretical/practice skill like System design — has no way to score under this model and is out of the taxonomy until a non-GitHub verification path exists. The weights are informed priors, not fitted; recalibrating them via logistic regression once outcome data (e.g. Technical Screen Pass Rate) exists is expected, not a violation of this decision. Volume being a required, nonzero component means a bare manifest listing alone no longer implies zero confidence — it produces a small Presence-only score instead (see `Declared-Only` in CONTEXT.md), which is a deliberate narrowing of the earlier "zero qualifying evidence → 0" guarantee, not an oversight.

**Depth discounts commit-message similarity relative to PR-comment similarity.** A commit message is authored solely by the Candidate, so it's directly gameable — writing an elaborate, skill-laden message on a trivial change costs nothing and would otherwise earn full Depth credit. A PR review comment is meaningfully harder to game, especially a reply in a thread someone else started. Rather than excluding commit messages from Depth outright — which would zero out Depth for solo/personal repos with no PR-review culture, exactly where a lot of real evidence lives — a commit message's cosine similarity is multiplied by a fixed discount (0.6) before entering `top_3` selection; PR-comment similarity is unaffected. Same "informed prior, calibrate later" status as the other constants in the formula.

**Volume must count only the Candidate's own, PR-verified commits — never every commit in a repo.** Counting file-pattern matches across an entire repository's history, unscoped, is directly gameable: fork a large, impressive repo and every prior commit's file touches would count toward Volume. The existing ingestion scoping (issue 03) already excludes forks from "owned" repos and fetches external-repo commits filtered to `author = candidate`, but that alone doesn't prove that a matched commit went through the merged PR the external repo was discovered by — a candidate with direct push access could bypass review entirely. Volume's commit set must be the intersection of (a) `author = candidate` and (b), for external (non-owned) repos specifically, "this commit is part of a PR the candidate opened that was actually merged" — not merely "this repo is one where some merged PR by the candidate exists." This must be stated explicitly in the implementation spec, not left implicit in ingestion's existing behavior, since a re-implementation of Volume could easily drop it.

## Considered Options

Keep pure embedding similarity (the original design) — rejected because code embeds too poorly against natural-language skill descriptions for the qualifying floor to mean anything for language/framework skills.
